تعرف syntax اللغة، تابعت عدة دورات، وتفهم الكود عندما تراه. لكن أمام صفحة فارغة لا تعرف من أين تبدأ. هذه ليست مشكلة نقص دورات غالبًا؛ إنها نقص ممارسة **تحويل المتطلبات إلى قرارات**.

## لماذا يحدث ذلك؟

في الدورة، المدرب اتخذ القرارات الصعبة مسبقًا: هيكل الملفات، ترتيب الخطوات، المكتبات، ونقطة البداية. عندما تعمل وحدك، تصبح أنت مسؤولًا عن هذه القرارات.

<div class="callout callout-info"><strong>الفرق:</strong> متابعة الحل تدربك على التعرف عليه. بناء المشروع يدربك على استدعاء المعرفة واختيار الحل.</div>

## استخدم مشروعًا أصغر مما تتوقع

بدل «سأبني متجرًا كاملًا»، ابدأ بـ:
1. قائمة منتجات ثابتة.
2. صفحة تفاصيل.
3. سلة محلية.
4. API.
5. قاعدة بيانات.
6. حساب مستخدم.
7. دفع تجريبي لاحقًا.

كل مرحلة يجب أن تعمل قبل التالية.

## قاعدة الـ30 دقيقة

عندما تتوقف:
- اقرأ الخطأ.
- حدد آخر شيء تغير.
- اصنع مثالًا أصغر للمشكلة.
- اقرأ التوثيق.
- ابحث أو استخدم AI بسؤال محدد.
- سجل الحل بعد فهمه.

<div class="callout callout-tip"><strong>نصيحة:</strong> احتفظ بملف `LEARNINGS.md` في مشاريع التدريب. اكتب فيه الأخطاء المهمة والسبب والحل. ستبني مرجعًا شخصيًا أفضل من حفظ عشرات الروابط.</div>

## لا تحذف النسخة السيئة

استخدم Git. احتفظ بالتاريخ. رؤية الفرق بين أول implementation والنسخة المحسنة جزء من التعلم.

```bash
git checkout -b feature/search
# نفّذ خطوة صغيرة
git add .
git commit -m "Add basic product search"
```

## متى تستخدم دورة جديدة؟

عندما تستطيع تسمية الفجوة: «لا أفهم SQL joins» أفضل من «أحتاج دورة Backend أخرى».

<div class="callout callout-important"><strong>التحدي:</strong> لمدة 14 يومًا، اجعل وقت البناء أكبر من وقت مشاهدة الدروس. لا تمنع التعلم؛ اجعله استجابة لمشكلة حقيقية في مشروعك.</div>
